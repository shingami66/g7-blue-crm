## 9. FINAL LAYER 1 PRODUCT MODEL

Layer 1 is one G7 BLUE operating system centered on an Event/Service, with authoritative records linked but never collapsed:

`Customer Need → Commercial Authority → Event Authority → Requirement → Supplier/Resource Commitment → Delivery/Acceptance → Actual Cost or Vendor Bill → Payable/Payment → Event Costing/Forecast → Closeout`

`Commercial Authority → Billing Authority/Schedule → Issued Invoice → Customer Payment → Allocation → Outstanding/Credit/Refund`

`Operational/Financial Source Records → Accountant-approved Mapping → Balanced Journal → Posting → GL/Reconciliation/Close → Financial Statements`

The product has three explicitly labeled truth planes:

- **Operational:** what must happen, who owns it, readiness, delivery, issues, and acceptance.
- **Managerial:** approved commercial value, budget, commitments, actuals, ETC/EAC, cash position, forecast/final margin, and performance analysis.
- **Accounting:** posted journals, GL, trial balance, reconciliation, close, revenue recognition, and financial statements under professional policy.

Configuration may select terminology, templates, thresholds, dashboard composition, approval matrices, document presentation, numbering, and default filters. It may not weaken authorization, auditability, separation of duties, financial invariants, correction history, confidentiality, or source traceability.

## 13. TARGET LAYER 1 TECHNICAL ARCHITECTURE

### 13.1 Shape

Use a modular monolith in the existing Next.js App Router repository. Keep Server Components as the default read/composition boundary, Client Components only for interaction state, Server Actions for first-party UI mutations, Route Handlers only for real HTTP/integration boundaries, and PostgreSQL transactions/RPCs where atomic financial invariants require them. Do not introduce services, event buses, generic workflow engines, generic dashboard builders, or tenant abstractions without measured need.

### 13.2 Domain modules

Future source modules are bounded by authority rather than page name:

- `authority`: permission catalog, templates, grants/denials, scopes, sensitive fields, approval policies, delegations, SoD exceptions;
- `commercial`: quotation authority, revisions, approval evidence and commercial change;
- `events`: brief, lifecycle, handoff, readiness, requirements, milestones, tasks, issues, team roles, resources, incidents and closeout;
- `procurement`: sourcing, quotes, comparison, commitment and receipt/acceptance;
- `expenses`: expense, reimbursement, advance and petty cash;
- `ap`: vendor bill, matching, dispute, payable and supplier payment;
- `ar`: billing schedule, invoice, allocation, receivable, corrections, credit and refund;
- `costing`: budget, contingency, event-cost entries, ETC/EAC and margins;
- `accounting`: mapping, journal, posting, ledger, reconciliation, period and statements behind professional activation;
- `reporting`: versioned metric definitions and permission-filtered read models; no source mutations;
- `action-center`: derived work index; source domains retain action authority.

### 13.3 Shared kernel

Keep the shared kernel deliberately small: stable identifiers, a generic money value of **amount + currency**, Riyadh business date/time, bilingual display values, actor/authority context, record version, reason/evidence reference, request/idempotency key, audit event envelope, and correction/supersession link. SAR is the G7 Layer 1 functional/default currency where applicable; the already-approved original/functional-currency FX seam remains explicit and is not replaced by a SAR-only assumption. A domain owns its lifecycle and invariants; shared UI or storage helpers do not own business policy.

### 13.4 Persistence rules

- Add records and states; never reinterpret historical rows silently.
- Monetary values use exact precision and currency; calculations define rounding stage and allocation reconciliation.
- Authoritative changes carry version, actor, timestamp, reason, and source evidence.
- Approved/issued/posted/paid/closed records are corrected or superseded, not hard-deleted.
- Source relationships use stable IDs; snapshots preserve the issued/approved representation where history must not drift.
- Every privileged database boundary is server-only, least-privilege, fail-closed, auditable, replay-aware, and independently reviewed.
- Formal accounting tables and posting functions do not activate before professional Gate PR-ACC.

### 13.5 Read architecture

Transactional tables remain source authority. Domain query modules return narrow server DTOs. Reports use versioned, reproducible read models only after source lifecycle definitions are stable. A metric definition includes identifier, business meaning, included/excluded states, business date, timezone, as-of behavior, source records, permissions/sensitive fields, currency/rounding, refresh policy, and drill target. Period, as-of, timezone, source, and freshness context is rendered once at the page/report header or section/metric-group boundary and inherited by its visuals; a card repeats context only when its meaning differs or it can be detached/exported. Do not require repetitive metadata on every card. Materialized views or caches require measured evidence and an explicit freshness/invalidation contract.

### 13.6 Integration seams

Preserve only documented integration boundaries. Do not create inactive adapter interfaces/contracts for bank, ZATCA/FATOORA, AI, or other future integrations when no current caller exists. Introduce an adapter only when a separately authorized real integration has a named caller, data contract, security review, environment, and Owner/professional gate. A documented boundary is not an implementation or activation.

### 13.7 Build and verification evidence

`built_from_head()` is exact build/verification evidence and remains outside the ERP runtime/domain shared kernel. It must never become a runtime field, domain dependency, or business rule.

## 17. DATA MIGRATION / CUTOVER / RECONCILIATION PLAN

No migration is authorized by this plan. Future migration work uses these gates:

### M0 Inventory and invariants

Record row counts, status distributions, null/orphan/duplicate checks, monetary totals, active-record uniqueness, audit coverage, and source-to-snapshot relationships for Customers, Services, Quotations/items, ABS/items, Invoices/items, Payments, Suppliers/rate cards/allocations/bookings, app users, and audit logs. Evidence excludes credentials and protected log contents.

### M1 Additive schema

Create new tables/columns/enums/functions as additive, nullable or safely defaulted structures. Do not rename or repurpose legacy statuses in the same step. Each migration states forward action, verification query, rollback/disable strategy, locking risk, privilege/grant changes, replay/idempotency behavior, and generated-type refresh.

### M2 Deterministic backfill

- Map each legacy Service status to a preserved `legacy_status` fact plus separate target commercial/payment/operational projections; never infer readiness solely from `Deposit Paid`.
- Map quotation, ABS, invoice, payment, supplier allocation, and booking identifiers to target source references without inventing approval, commitment, receipt, allocation, revenue, or cost facts.
- Backfill only values derivable without judgment. Ambiguous records enter an exception queue with reason and Owner/professional resolution ownership.
- Preserve issued snapshots, dates, amounts, audit events, and legacy identifiers.

### M3 Shadow reconciliation

For each domain compare legacy and target counts, monetary sums by currency/status/period, relationship coverage, duplicate keys, orphan keys, status mapping, and sample record timelines. Financial reconciliation tolerance is exact at stored precision; no unexplained balancing entry or silent rounding adjustment is allowed.

### M4 Compatibility period

Read target projections behind an explicit feature/config gate while source writes remain on the approved authority path. Avoid indefinite dual write. A compatibility read or mapping seam is permitted only when it documents the existing source boundary; do not create an adapter interface or contract without a current caller. If a separately authorized real integration later requires an adapter, it must have a named caller, fixed removal criterion, replay protection, observability, and rollback to the last authoritative source.

### M5 Controlled cutover

Cut over one domain at a time after DEV/DEMO rehearsal, independent migration review, Mozfer workflow acceptance, professional sign-off where required, backup/restore proof, maintenance/communication plan, and explicit environment authority. Freeze only the affected mutation surface for the shortest proven interval.

### M6 Post-cutover proof

Repeat reconciliation, inspect exception queues, verify permissions/grants, test representative workflows in English and Arabic/RTL/mobile, confirm reports/as-of trace to sources, and retain rollback capability through the defined stabilization window. Remove legacy paths only in a later separately reviewed change after usage evidence shows no dependency.

## 20. MOZFER 8-HOUR DAILY EXECUTION PROGRAM

The 8-hour model is a capacity budget, not a clock-by-clock schedule. The Controller allocates the day in this order, with the exact duration adjusted to the slice:

1. **Orient and protect (budget 0.5–1 hour):** reverify `HEAD`, dirty/protected boundary, current workflow evidence, dependency, authority status, and the exact mutation manifest.
2. **Daily Core (budget normally 4.5–6 hours):** one bounded slice only. 3. **Validation and repair (budget 0.75–1.25 hours):** focused tests, type/lint/build checks appropriate to the slice, then same-Writer repair of confirmed findings.
4. **Review and acceptance (budget 0.75–1.5 hours):** independent findings-only review and Mozfer manual acceptance where the slice changes behavior or presentation.
5. **Evidence closeout (budget 0.25–0.75 hour):** record the evidence boundary, status (`PASS`, `PASS WITH WARN`, `PARTIAL`, `HOLD`, or `FAIL`), remaining gate, documentation delta, and one exact next action.

These are capacity envelopes, not additive appointments; the Controller caps normal engineering work at approximately eight hours and rebalances the ranges around the slice. The Daily Core must close at a durable evidence boundary; unfinished work is not silently carried as if complete. External professional-review waiting time is a gate recorded as `HOLD` or `PARTIAL`, not automatically one normal engineering day and not a reason to start an adjacent wave. If a database, Owner, or professional gate is closed, the day stops at that gate and records the precise missing authority.
